Важно: это не просто новая версия бинарника, а заметно другая архитектура.

### Главное отличие

В `nfqws1` методы обхода жёстко реализованы внутри C-кода:

```text
--dpi-desync=fake,multisplit
--dpi-desync-fooling=md5sig
--dpi-desync-split-pos=1,midsld
```

В `nfqws2` движок анализирует и перехватывает пакеты, а воздействие на них выполняют Lua-функции:

```text
--lua-init=@zapret-lib.lua
--lua-init=@zapret-antidpi.lua
--payload=tls_client_hello
--lua-desync=fake:blob=fake_default_tls:tcp_md5
--lua-desync=multisplit:pos=1,midsld
```

Из этого следуют основные различия:

| Область | `nfqws1` | `nfqws2` |
|---|---|---|
| Стратегии | Зашиты в бинарник | Программируются на Lua |
| Расширение возможностей | Требует изменения C-кода | Можно написать Lua-стратегию |
| Формат конфигурации | `--dpi-desync-*` | `--lua-desync`, `--payload`, `--blob` |
| Обработка пакетов | Фиксированные фазы desync | Произвольная последовательность Lua-функций |
| Направления трафика | В основном исходящее воздействие | Полноценная работа с входящим и исходящим |
| Ограничение обработки | `start/cutoff` | Гибкие `--in-range` и `--out-range` |
| Fake-пакеты | Отдельные параметры для HTTP/TLS/QUIC | Именованные бинарные `blob` |
| Развитие | EOL, только исправления | Актуальная развиваемая версия |

Например, в `nfqws2` можно последовательно:

1. изменить пакет;
2. отправить несколько разных fake;
3. применить к каждому отдельные TTL/SEQ/ACK;
4. разрезать оригинал;
5. изменить порядок сегментов;
6. отдельно обработать ответ сервера.

У первого поколения подобные сценарии ограничены заранее предусмотренными комбинациями.

### Что изменилось в тестере

`blockcheck2.sh` выполняет ту же основную задачу — перебирает методы и проверяет запросы через `curl`. Но результаты у него уже в формате `nfqws2` с Lua-вызовами. Перечень тестов модульный: стратегии лежат отдельно в `blockcheck2.d`, поэтому их проще добавлять и изменять без переписывания основного тестера.

Результаты этих двух тестеров нельзя смешивать:

- `blockcheck.sh` → конфиги для `nfqws1`;
- `blockcheck2.sh` → конфиги для `nfqws2`.

### Что это означает для нашего проекта

Сейчас проект полностью построен вокруг `nfqws1`. Просто заменить бинарник не получится. Потребуется:

- заменить `nfqws` на `nfqws2`;
- добавить Lua-библиотеки и fake-файлы;
- переписать все стратегии YouTube и WhatsApp;
- изменить сборку временного конфига;
- пересмотреть `iptables`: `nfqws2` умеет полноценно обрабатывать оба направления, а текущий скрипт отправляет в очередь только исходящий `OUTPUT`;
- адаптировать логирование и определение профилей;
- отдельно учесть серверный режим `--server`.

Моё предварительное мнение: для долгосрочного развития разумнее переходить на `nfqws2`, особенно если планируется автоматический подбор стратегий. Но это будет миграция подсистемы, а не небольшой апгрейд. Текущий `nfqws1` проще и уже встроен в проект, зато больше не получает новых возможностей.

АССИСТЕНТ:
`test-strategies.sh` автоматически перебирает разные способы изменения пакетов и проверяет, какой из них позволяет открыть заблокированный домен с конкретного сервера.

Общая схема:

```text
домен → запрос без обхода → перебор стратегий → повторные запросы → SUMMARY
```

### Как запустить

Для выбранного в `.env` движка:

```bash
sudo ./test-strategies.sh youtube.com googlevideo.com
```

Или интерактивно:

```bash
sudo ./test-strategies.sh
```

Во втором случае официальный tester сам спросит домены и параметры проверки.

### Что происходит внутри

1. Читается `.env`:

```dotenv
NFQWS_ENGINE=1
```

или:

```dotenv
NFQWS_ENGINE=2
```

2. Запущенный 3B останавливается.

Это необходимо, иначе уже активная стратегия будет влиять на запросы, и tester получит ложный результат.

3. Выбирается совместимый tester:

- `NFQWS_ENGINE=1` → `blockcheck.sh` и `nfqws1`;
- `NFQWS_ENGINE=2` → `blockcheck2.sh` и `nfqws2`.

4. Проверяется обычное соединение без обхода:

- DNS;
- доступность IP и порта;
- HTTP;
- HTTPS с TLS 1.2 и TLS 1.3;
- QUIC/HTTP3, если установленный `curl` это поддерживает.

5. Tester временно создаёт собственную NFQUEUE и правила firewall.

6. Затем перебираются стратегии, например:

- разрезание TCP-запроса;
- изменение порядка сегментов;
- sequence overlap;
- отправка fake-пакетов;
- изменение TTL;
- неправильные SEQ/ACK;
- комбинации fake и split;
- отдельные варианты для QUIC.

7. После каждой стратегии выполняется запрос через `curl`.

Если запрос успешно завершается, стратегия записывается как рабочая. Если включены повторы, успех должны подтвердить несколько запросов.

8. В конце временные процессы и правила tester-а удаляются, а результаты выводятся в секции `SUMMARY`.

### Важные ограничения

Tester проверяет доступность через `curl`. У браузера, YouTube-приложения или WhatsApp может быть другой сетевой fingerprint, поэтому найденная стратегия не гарантирует работу всего приложения.

Особенно это касается YouTube: проверка главной страницы ещё не подтверждает воспроизведение видео с `googlevideo.com`. Поэтому желательно тестировать несколько связанных доменов:

```bash

  youtube.com \
  googlevideo.com \
  youtubei.googleapis.com \
  ytimg.com
```

Для WhatsApp:

```bash
sudo ./test-strategies.sh \
  whatsapp.com \
  web.whatsapp.com \
  static.whatsapp.net
```

Звонки и медиа WhatsApp используют UDP и дополнительные адреса, поэтому обычная HTTPS-проверка подтверждает только веб-доступ, но не гарантирует работу звонков.

Да, это как раз рабочий подход. Но не через простую «подмену IP»/DNAT: WhatsApp использует TLS, проверяет сертификаты, множество IP и UDP. Если заменить адрес назначения на произвольный прокси, соединение сломается.

Нужна прозрачная маршрутизация через второй сервер вне блокировки:

```text
клиент
  → текущий 3x-ui
  → трафик WhatsApp
  → туннель до второго VPS
  → интернет/Meta
```

Лучший вариант — второй VPS + WireGuard. Он прозрачно переносит:

- TCP 443;
- UDP 443/QUIC;
- порты звонков и STUN;
- исходные домены, SNI и сертификаты без подмены.

На текущем сервере policy routing направляет только сети Meta через WireGuard, остальной трафик идёт как раньше:

```text
WhatsApp/Meta IP → wg0
остальной трафик → основной gateway
```

Альтернатива внутри 3x-ui:

- поднять на втором VPS VLESS;
- добавить его как outbound на первом сервере;
- создать routing rule по доменам `whatsapp.com`, `whatsapp.net`, `cdn.whatsapp.net`;
- при необходимости добавить IP/CIDR Meta.

Это проще встроить в существующий 3x-ui, но нужно внимательно настроить DNS и UDP. WireGuard с policy routing обычно надёжнее для звонков.

Что не подойдёт:

- DNAT IP WhatsApp на IP прокси;
- изменение `/etc/hosts`;
- обычный HTTP-прокси только для HTTPS;
- один фиксированный IP — WhatsApp использует много подсетей и CDN.

Практичная архитектура:

1. Арендовать небольшой VPS там, где `nc IP 443` до Meta проходит.
2. Соединить серверы WireGuard.
3. На втором включить forwarding и NAT.
4. На первом создать отдельную routing table через `wg0`.
5. Помечать назначения из `ipsets/whatsapp-ips.txt`.
6. Отправлять только эти пакеты в таблицу WireGuard.
7. DNS WhatsApp получать через незаблокированный resolver/DoH.
8. `nfqws` оставить для YouTube, а WhatsApp исключить из NFQUEUE или пустить раньше через policy routing.

То есть да: второй незаблокированный выход решит IP-блокировку. Я бы делал именно WireGuard-маршрут для Meta, а не подмену адресов.

### Что действительно работает

#### 1. Полноценный туннель через зарубежный сервер

Это самый надёжный вариант для:

- сообщений;
- изображений и файлов;
- уведомлений;
- голосовых и видеозвонков;
- UDP/QUIC/STUN.

Для твоей схемы оптимально:

```text
клиент → текущий 3x-ui → второй VPS вне блокировки → WhatsApp
```

Туннель между VPS можно сделать через WireGuard, AmneziaWG или второй VLESS-outbound. Направлять туда можно только WhatsApp/Meta, оставляя YouTube на `nfqws2`.

Твои измерения подтверждают необходимость такого выхода:

```text
157.240.0.60:443 — TCP handshake не проходит
31.13.72.52:443 — TCP handshake не проходит
```

При таком L4/IP-блоке стратегии `fake`, `split`, `multidisorder` не помогут.

#### 2. Официальный WhatsApp Proxy

У WhatsApp есть собственная серверная реализация proxy, которую можно поднять на зарубежном VPS. Она предназначена для подключения приложения к чатам:

[официальный репозиторий WhatsApp Proxy](https://github.com/WhatsApp/proxy).

Преимущества:

- встроенная поддержка в мобильном приложении;
- не нужно туннелировать весь телефон;
- работают сообщения и TCP-медиа;
- относительно простое развёртывание через Docker.

Ограничение критичное: официальный proxy поддерживает только TCP и прямо указывает, что VoIP сейчас не поддерживается. Следовательно, звонки через него не заработают. [Официальный README](https://github.com/WhatsApp/proxy), [официальный FAQ](https://github.com/whatsapp/proxy/blob/main/FAQ.md).

Подходит, если нужны прежде всего чаты.

#### 3. Зашифрованный DNS

DoH/DoT/dnscrypt помогает, когда блокировка ограничивается удалением DNS-записей. У тебя Quad9 DoH уже работает:

```text
https://dns.quad9.net/dns-query : OK
```

Но DNS решает только получение IP. Он не исправит timeout на уже известном `157.240.0.60:443`.

То есть DoH нужен в любом случае, но конкретно на твоём VPS его недостаточно.

#### 4. Zapret/nfqws

В сообществе Zapret существуют рабочие рецепты для некоторых российских провайдеров, особенно когда соединение до Meta устанавливается, а DPI ломает TLS или отдельные пакеты. Есть отдельное обсуждение с пользовательскими стратегиями: [WhatsApp: обход замедления/блокировки](https://github.com/bol-van/zapret/discussions/1908).

Однако эти рецепты зависят от провайдера. На твоём маршруте порт 443 не устанавливает TCP-соединение, поэтому Zapret не получает TLS ClientHello, к которому можно применить стратегию.

ПОЛЬЗОВАТЕЛЬ:
Окей давай поймем как вообще работает тест стратегий. Там типа идет и тест же смешанных стратегий?


АССИСТЕНТ:
Да, тестер проверяет как одиночные, так и некоторые смешанные стратегии. Но он не перебирает вообще все математически возможные сочетания.

Как устроен тест

Для каждого домена и протокола `blockcheck2` сначала проверяет соединение без обхода:

```text
curl_test_https_tls12 ipv4 youtube.com
checking without DPI bypass
```

Если сайт без обхода недоступен, tester временно создаёт перенаправление в NFQUEUE и последовательно запускает набор сценариев из:

```text
vendor/zapret2/blockcheck2.d/standard/
```

Каждая строка такого вида — одна самостоятельная проверяемая стратегия:

```text
nfqws2 --payload=tls_client_hello --lua-desync=multidisorder:pos=1,midsld
```

Она запускается отдельно, затем `curl` делает заданное количество попыток.

Если все `REPEATS` успешны:

```text
!!!!! AVAILABLE !!!!!
```

наша обёртка сохраняет стратегию.

Одиночные стратегии

Например, только разбиение ClientHello:

```text
--payload=tls_client_hello
--lua-desync=multidisorder:pos=1,midsld
```

Или только отправка фейка:

```text
--payload=tls_client_hello
--lua-desync=fake:blob=fake_default_tls:repeats=2
```

Или OOB:

```text
--in-range=-s1
--lua-desync=oob:urp=midsld
```

Смешанные стратегии

Да, tester также проверяет заранее предусмотренные цепочки:

```text
--lua-desync=fake:blob=fake_default_tls:tcp_md5
--lua-desync=multidisorder:pos=midsld
```

Здесь сначала создаётся фейковый TLS-пакет, затем настоящий ClientHello разбивается или переставляется.

Другой пример:

```text
--lua-desync=tcpseg:pos=0,-1:seqovl=1
--lua-desync=drop
```

Или более сложная цепочка:

```text
--lua-desync=fake:blob=0x00000000:tcp_md5
--lua-desync=fake:blob=fake_default_tls:tcp_md5:tls_mod=rnd,dupsid
--lua-desync=multisplit:pos=2
```

Все строки `--lua-desync` внутри одной выводимой команды образуют одну смешанную стратегию и проверяются совместно.

Что означает `standard`

Сценарии идут примерно такими группами:

1. Базовые модификации HTTP.
2. TCP segmentation.
3. OOB.
4. `multisplit` и `multidisorder`.
5. Sequence overlap.
6. SYN-data.
7. Fake TLS.
8. Fake + split/disorder.
9. Hostfake.
10. Различные fooling-параметры.
11. QUIC, если curl поддерживает HTTP/3.

`standard` использует адаптивный перебор: если в группе найден рабочий вариант, некоторые более тяжёлые варианты могут быть пропущены.

Разница режимов

```dotenv
STRATEGY_TEST_LEVEL=quick
```

После раннего успеха агрессивно прекращает дальнейший перебор соответствующей ветки.

```dotenv
STRATEGY_TEST_LEVEL=standard
```

Проверяет основные одиночные и предусмотренные смешанные стратегии, но сокращает некоторые ветки после успеха.

```dotenv
STRATEGY_TEST_LEVEL=force
```

Старается прогнать все варианты, перечисленные в официальных сценариях, даже если более простой вариант уже сработал. Это значительно дольше.

Чего tester не делает

Он не берёт каждую найденную стратегию и не скрещивает её со всеми остальными. Например, он автоматически не перебирает декартово произведение:

```text
каждый fake × каждый fooling × каждый split × каждый repeats
```

Таких комбинаций было бы огромное количество.

Он проверяет только комбинации, которые авторы zapret2 заранее внесли в стандартные сценарии. Поэтому твой готовый профиль:

```text
fake + multidisorder
```

будет проверен только в том случае, если соответствующая комбинация присутствует в одном из tester-скриптов.

Главный принцип чтения результата

Одна строка:

```text
curl_test... : nfqws2 <все параметры>
```

— это одна цельная стратегия.

Если после неё:

```text
!!!!! AVAILABLE !!!!!
```

значит именно вся указанная комбинация успешно прошла настроенное количество повторов. Нельзя брать только половину параметров и считать её проверенной.

ПОЛЬЗОВАТЕЛЬ:
А если вот нашли стратегии, но еще тест не прошел - то при ctrl+C сохранятся стратегии?


АССИСТЕНТ:
Да. Каждая успешная стратегия сохраняется сразу после появления:

```text
!!!!! AVAILABLE !!!!!
```

и сообщения:

```text
>>> FOUND: ...
>>> SAVED: ...
```

Поэтому после этого можно нажать `Ctrl+C` — уже найденные стратегии останутся в:

```text
logs/tests/results/nfqws2-ДАТА-ВРЕМЯ/domains/<домен>/
```

Все найденные варианты:

```text
tls12-ipv4.all.conf
```

Первый успешный кандидат:

```text
tls12-ipv4.candidate.conf
```

Живой индекс:

```text
index.live.tsv
```

Проверить последний результат:

```bash
./show-strategies.sh
```

Либо найти последний каталог:

```bash
find logs/tests/results -mindepth 1 -maxdepth 1 -type d \
  -printf '%T@ %p\n' |
  sort -nr |
  head -n1
```

Важно:

- если на экране уже появился `>>> SAVED`, стратегия точно записана;
- если `curl` ещё выполняет её попытки и `FOUND` не появился, незавершённая стратегия не сохранится;
- при `Ctrl+C` не будет финального `SUMMARY`, `common/` и окончательного `index.tsv`;
- ранее сохранённые `*.all.conf`, `*.candidate.conf` и `index.live.tsv` останутся;
- временные правила tester-а должны удалиться обработчиком завершения.

Для максимально штатной остановки лучше использовать:

```dotenv
STRATEGY_TEST_STOP_AFTER_FOUND=15
```

Тогда tester остановится сам сразу после полностью проверенной пятнадцатой находки.

ПОЛЬЗОВАТЕЛЬ:
Хм... А если сделать еще один режим типа умного режима? Который сначала перебирает какое то кол.во стратегий, а потом он начинает из найденных делать микс и усложнять стратегии? Пока не добавляй, просто вот думаю как варик


АССИСТЕНТ:
Да, идея хорошая. Это можно сделать как отдельный режим, условно:

```dotenv
STRATEGY_TEST_LEVEL=smart
```

Он мог бы работать в несколько фаз.

1. Поиск базовых компонентов

Сначала проверять сравнительно дешёвые одиночные методы:

```text
tcpseg
multisplit
multidisorder
oob
fake
hostfake
syndata
```

Допустим, собрать первые 10–20 стабильных результатов.

2. Разбор найденных стратегий

Не смешивать строки вслепую, а разобрать их на компоненты:

```text
payload
range
fake
packet modification
split/disorder
drop
```

Например:

```text
A = fake:blob=fake_default_tls:tcp_md5
B = multidisorder:pos=1,midsld
```

3. Создание совместимых комбинаций

Из результатов сформировать осмысленные цепочки:

```text
fake + multidisorder
fake + multisplit
packet modification + fake + split
syndata + split
```

Но не создавать заведомо конфликтные комбинации:

```text
несколько альтернативных split-методов одновременно
несовместимые payload
TLS-модификатор для HTTP
TCP-метод для QUIC
```

4. Повторная проверка

Каждая новая комбинация проходит обычные `REPEATS`. Успешные варианты сразу записываются отдельно:

```text
domains/youtube.com/tls12-ipv4.smart.all.conf
domains/youtube.com/tls12-ipv4.smart.candidate.conf
```

5. Усложнение только при необходимости

Если простая стратегия работает стабильно, нет смысла сразу превращать её в огромную цепочку. Можно использовать уровни сложности:

```text
одиночная
  → два совместимых компонента
    → три компонента
      → вариации fooling/repeats/позиции
```

И прекращать усложнение, когда достигнута заданная цель.

Какие параметры пригодились бы

```dotenv
STRATEGY_TEST_LEVEL=smart

# Сколько базовых успешных вариантов собрать
STRATEGY_SMART_BASE_TARGET=15

# Сколько успешных смешанных вариантов найти
STRATEGY_SMART_MIX_TARGET=10

# Максимальное число lua-desync в комбинации
STRATEGY_SMART_MAX_DEPTH=3

# Сколько повторов для предварительного отбора
STRATEGY_SMART_SCREEN_REPEATS=1

# Сколько повторов для финальной проверки
STRATEGY_SMART_FINAL_REPEATS=5
```

Правильнее использовать двухступенчатую проверку:

```text
много кандидатов × 1 быстрая попытка
               ↓
лучшие кандидаты × 5 финальных попыток
```

Это будет быстрее, чем проверять каждую экспериментальную комбинацию по пять раз.

Основные риски

- Комбинация двух рабочих методов не обязательно будет рабочей.
- Слишком сильный desync может ломать соединение уже на стороне сервера.
- Число сочетаний растёт очень быстро.
- Некоторые действия должны идти строго в определённом порядке.
- Стратегия, успешная в `curl`, может плохо работать в браузере или приложении.
- Нельзя смешивать результаты разных доменов, протоколов, IP-версий и движков.

Поэтому я бы делал это не как случайный генератор, а как небольшой планировщик с таблицей совместимости и ограничением сложности. Особенно полезен smart-режим будет после обычного `standard`: он возьмёт уже подтверждённые строительные блоки и исследует только разумные комбинации.

Идея перспективная, но сначала стоит накопить реальные результаты YouTube и WhatsApp — по ним будет видно, какие семейства методов действительно имеет смысл смешивать.

```bash
sudo pkill -f nfqws
```

То есть он убивает только что запущенный `nfqws2`. Более того, следующие команды сносят вообще всю таблицу `mangle`, включая чужие правила:

```bash
iptables -t mangle -F
iptables -t mangle -X
```

Замени `/etc/systemd/system/3b-dpi.service` целиком:

```bash
sudo nano /etc/systemd/system/3b-dpi.service
```

```ini
[Unit]
Description=3B DPI Bypass System
Wants=network-online.target
After=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/home/superrootpx/3B
ExecStart=/home/superrootpx/3B/start.sh
ExecStop=/home/superrootpx/3B/stop.sh
TimeoutStartSec=60
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable 3b-dpi.service
sudo systemctl restart 3b-dpi.service
sudo systemctl status 3b-dpi.service --no-pager
```

Нормальный статус будет примерно таким:

```text
Active: active (exited)
```

Это нормально для `Type=oneshot`: сам `nfqws2` продолжает работать в фоне.

```bash
sudo systemctl start 3b-dpi
```
